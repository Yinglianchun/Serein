## 摘要

长期对话中的一段经历可能跨越多日、与其他话题交错，甚至与另一段经历共享同一条消息。将此类对话整理为 Event，需要持续组织交错消息，在后续信息到达后确定经历边界，并在更新时保留可追溯的来源与续接关系。本文介绍源于长期人机亲密互动的 Serein 记忆系统中的 Event 处理管线：Track Router 持续归线，Curator 在延迟结算时选择经历并确定来源归属，Writer 依据既定归属生成正文，宿主程序保存来源角色与续接关系。原始消息独立保留，Track 摘要用于定位和承接话题。

本文通过局部判断、事务适配器多日回放、隔离真实服务执行和两段选定自然对话的重新分组，考察持续归线、延迟结算与来源追溯如何衔接。一组 66 条合成消息的真实服务回放完成五次单前身续接，旧来源全部保留，提交的来源集合与保存后读回一致；同次执行也出现例行早餐误收与原文漏传。其他案例定位了共享来源角色丢失、合法共享误拒绝和空前文处理中断。连续材料展示了跨日承接，稳定窗口案例则揭示了延迟结算对最新纠正可见性的影响。来源集合、自检结果和正文的交叉核对进一步表明，来源追溯需要覆盖从输入组装到修订保存的各个阶段。现有证据支持所列实现与案例分析，尚不足以估计总体准确率、相对性能或下游效果的独立贡献。

## 1. 引言

Serein 的经历记忆设计来自一位使用者与其个人 AI 助手的长期亲密互动。日常对话同时容纳共读、一起做饭、生活交流与系统开发；使用者希望保留其中形成具体展开的经历，并让后续进展、纠正和重新理解回到相应记录。由此形成三项设计要求：经历应保持可辨识，记忆依据应能够追溯，后续修订应保留与前版的关系。虽然这一场景可能与其他长期个人 agent 的需求相交，本文的 Event 定义仍以本系统的记录偏好为前提。

一段工程讨论可能在午饭后继续，又在次日验证时回到对话中；旅行、作品讨论和生活汇报则交错其间。若以每次沉默或每个自然日划定记忆边界，同一经历会被拆散；若仅按关键词聚合，日常“吃了蛋饼”又可能被并入前一天共同做饭的记忆。系统因此必须区分三个问题：当前材料延续哪条话题线，是否形成值得保存的经历，以及每条原文具体支持哪一条记忆。

本文将 Event 定义为一段具有可追溯来源、能够独立叙述的经历。它不必包含重大决定或戏剧性变化；围绕具体内容形成的感受、理解与回应同样可以构成经历。反之，内容具体、篇幅较长或包含操作结果，也不会自动满足记录条件。简短状态在实质承接既有经历时，可以成为其结果或后续。

本文围绕 Event 构建与更新给出三项相互衔接的系统设计：（1）持续归线，将交错到达的消息组织到可延续的 Track；（2）延迟结算，将话题追踪与 Event 入选、边界及续接对象的判断分开；（3）来源追溯，通过来源归属、来源角色和显式续接关系，保留更新依据并定位传递中的错误。案例评价沿阶段输入、模型原始输出和保存状态展开，分别检查这些设计的实际行为。

使用者参与需求提出、案例讨论和部分结果裁定，开发过程也使用模型协助实现与审阅。本文据此报告参与式开发过程及其系统案例；使用体验与评价限制见 §6.2。

## 2. 相关工作与研究范围

与本文最相关的研究可分为三类：长期人机关系与陪伴记忆、交错对话的分离与分段，以及个性化和长期记忆的下游评价。

在人机关系研究中，Skjuve 等访谈了十八位与 Replika 建立友谊的参与者，讨论关系发展、信任与自我披露。其研究为理解持续互动提供了背景；本文所述人机亲密互动则提出了保留共同经历、支持后续修订的系统需求。[Skjuve et al., 2021](https://doi.org/10.1016/j.ijhcs.2021.102601)

Conversation disentanglement 研究如何从混合消息流中恢复会话及其内部结构。Kummerfeld 等提供了带回复结构和标注分歧裁定的数据集；SuperDialseg 则讨论对话分段点的定义及标注困难。这些工作为交错消息的关系恢复和边界标注提供了参照。Serein 还处理跨日续接与有界来源重叠，因此除时间序列上的切点外，还需检查非连续消息之间的归属及继承关系。[Kummerfeld et al., 2019](https://aclanthology.org/P19-1374/)、[Jiang et al., 2023](https://aclanthology.org/2023.emnlp-main.249/)

长期记忆系统方面，Generative Agents 将经历记录、反思与检索纳入代理架构，MemGPT 则通过分层记忆管理扩展可用上下文。保存记录并按需读取已有研究基础，本文进一步检查记忆形成时的来源归属及其在更新中的传递。[Park et al., 2023](https://arxiv.org/abs/2304.03442)、[Packer et al., 2023](https://arxiv.org/abs/2310.08560)

MemoryBank 与本文的应用动机最为接近：它面向长期交互，将带时间的历史对话、日级与全局事件摘要、用户画像结合，并实现记忆检索与更新。Serein 同样服务于持续互动，其案例分析集中于记忆形成阶段：交错消息如何持续归线，经历边界如何在延迟结算时确定，以及来源角色和续接关系如何跨阶段保持。这里区分的是本文的检查对象，而非对 MemoryBank 能力或性能的判定。[Zhong et al., 2023, v3 §2](https://arxiv.org/html/2305.10250v3)

在下游评价方面，LaMP 以用户历史条目支持个性化分类和生成，LongMemEval 则覆盖信息提取、多会话推理、时间推理、知识更新与拒答，并区分索引、检索和阅读。这些工作提供了从记忆构建延伸到输出质量的评价视角，与本文对 Event 形成和更新过程的检查相衔接。[Salemi et al., 2024](https://aclanthology.org/2024.acl-long.399/)、[Wu et al., 2024; 修订版 2025](https://arxiv.org/abs/2410.10813)

## 3. 系统设计

本节依次说明归线、经历选择、来源传递与保存机制，再用一组交错对话展示这些判断如何衔接。§3.1–3.7 说明核心机制，并以 E1–E9 展示其演变；图 1 概括当前处理职责，§3.8 单列实验后的实现修订与局部试验 E10，§3.9 简述 Event 保存后的使用接口。各次执行的版本条件见 §4；后续修订不追溯计入旧实验条件。

### 3.1 数据对象与职责

处理管线在保留原始消息的基础上组织两类核心对象：Track 是持续追踪话题的线索，Event 是经过选择并绑定来源的经历记录。持续归线是将当前消息组织到新建或已有 Track；续接是让后续进展更新已有 Event，并保存前身与后继之间的续接关系。Track 可以持续存在而不产生 Event，其边界也不直接等于 Event 边界。下文将负责组装模型输入、检查约束和结算结果的程序称为宿主。本文历史实现及自用部署中的聊天宿主名为 Haven Bridge，后文简称 Bridge；公开发行版的落库边界另见 §3.8。“输入合同”指当轮明确交给模型的可见范围、归属单元与输出约束。

原始消息以稳定标识保存。完整对话用于调度和完整性判断；归属单元（unit）是模型必须整体处置的来源集合；Track 组件（component）按已声明的跨线关系界定联合阅读范围。对象定义与职责见[表 S2](supplementary-tables.md#表-s2-数据对象与处理职责)。

### 3.2 时间窗口与经历边界

在所述实现中，日间 Router 只在同一会话累计至少五个已完成回复包、且最后一条可回应消息之后出现 20 分钟会话静默时处理材料；凌晨 03:00 的结算则通过稳定窗口选择可处理原文。助手发出的普通回复或主动消息会重新开启回应窗口。未获回答的普通提问或主动消息不凑轮数；主动消息获得使用者首条回复后，整段交互只计一个完整回复包。持续聊天会继续后移处理时点，中途已经形成 20 分钟停顿时则可先处理停顿前的完整部分，不同会话不合计。

这一时间规则只粗分处理批次，不承担话题或经历切分。白天 Router 处理达到门槛的完整回复包；凌晨结算时，未完成或仍在最后 20 分钟内的尾部可以作为 parked 上下文与稳定材料一同进入 Router 阅读范围，由 Router 逐条判断所属 Track，但 Curator 不把 parked 尾部当作本轮稳定来源。满足当轮完整性和时间条件的材料称为稳定材料（stable），其余内容继续留在缓冲区。因而 20 分钟无回应并不直接产生一条 Event：次日结果仍可续接已有 Event，同一时间段也可以形成多条经历。各次实验是否执行完整日批，见第 4 节。

Track 卡本身不设删除 TTL。公开 API 上游不必提供窗口身份；每次归线读取同一来源、同一运行环境下，在配置回看天数内实际归入过原话的卡片。再次使用会刷新最近归线锚点，超期 Track 不再参与 Router，但仍保存在数据库中。因此，Track 的持久保留与模型当批可见范围是两个不同条件。

稳定窗口也会引入延迟。E3 模拟 03:00 结算时，稳定截止为 02:40；02:55 发出但尚未获回复的纠正仍在缓冲区，未进入 Curator 输入。原测试曾将其记为错误，复核输入后改判为既定完整性与窗口规则下的延迟。若希望尚未完整的最新消息也能阻止旧结论结算，还需另行定义其可见范围与延后条件。

### 3.3 入选与承接

本系统的入选依据是：对话是否围绕具体内容形成实质展开，或是否实质承接已有经历。展开可以推进理解、感受或经历进程，也可以体现为双方共同发展一个玩笑、比喻或具体体验；例行询问、单纯状态回报、一般确认和提醒则可以跳过。判断不依赖“吃饭”“工程”等题材白名单，也不设固定篇幅门槛。

例如，“改了吗—改了—早点休息”在缺少其他前情时可能只是进度确认；若此前已经讨论如何婉拒聚会并另约见面，“照刚才那个发了”便确认了表达方案的落实，可以续入原经历。使用者在实验后确认了这一具体判断（§4.5）。决定作用的不是句子长短，而是它与前情之间的实质关系。

普通 Track 按具体经历判断承接。只有当输入显式指定 `event_policy=rolling_engineering` 时，系统才采用较粗的工程粒度：只要局部排错、修改与验证仍服务于同一持续建设目标，就保持为一条 Event；原建设明确结束或转向另一项独立建设时再分开。

Curator 为稳定单元选择以下处置。处理时点不满足条件的材料可以暂留缓冲区；这种等待与模型输出的 defer 分别记录。

`create` 创建新 Event；`extend` 选择一个前身续接；`merge` 选择至少两个前身形成后继；`skip` 跳过材料；`defer` 按合同暂缓。前身与保护条件见[表 S3](supplementary-tables.md#表-s3-curator-处置与前身条件)。

### 3.4 阅读范围、来源归属与来源角色

阅读范围与最终归属是两个层次。`owned` 表示绑定到当前 Event 的来源；`context_only` 只用于理解对象、起因或指代，不会自动成为 Event 来源。对本轮稳定单元，模型必须将其完整分配给某条 Event，或标记为 skip/defer。

来源角色进一步说明原文应如何使用。`primary_activity` 表示服务当前经历的主活动，`bridge` 表示跨经历衔接的共享来源。只有经 Router 声明且满足约束的 bridge 单元可以同时支持多个 Event；写作时，每条 Event 仍只使用其中与自身相关的内容。完整处理一组问答，并不意味着问与答都应共享归属。§3.7 展示了一条消息服务两段经历、其回复只服务其中一段的情形。

续接或合并时，被选中的旧 Event 称为前身（base），新记录称为后继，二者之间保留显式续接关系。来源归属限定每条 Event 可以使用和继承的消息范围；后继来源取所有前身来源与本轮 owned 来源的并集。普通续接继承已有来源角色，显式纠错和重新归属另行记录。来源追溯据此检查“依据在哪里”“如何使用依据”及“依据如何沿续接关系传递”。§5.3 展示了标识仍在、角色却在输入重建中丢失的后果。

当整个组件缺少对象、起因或被纠正的旧主张时，Curator 可以申请一次有界补读；补读范围受 Track、会话与消息位置限制。Track 的存在并不保证范围内确有更早原文，因此空结果必须与越界请求、原文损坏分别处理。§5.8 分析了空读取未被正确返回所造成的故障。

### 3.5 写作与持久化

Writer 直接接收原文阅读块、来源角色与既定 Event 计划，输出正文及自检字段。来源追溯依靠原文绑定和角色传递，不以另一次模型生成的证据摘要为前提。宿主可以验证结构、标识和集合关系；语句是否忠实、是否把建议写成事实，仍需核读正文。自检字段为真只能视为模型自报，不能替代语义审阅。

结算阶段同时保存新记录与修订关系。被替换的旧记录继续保留并标记为已被替代（superseded），active 则表示当前有效记录。处理游标（cursor）只记录进度；本文另行核对提交内容、保存后读回与续接关系，避免把游标推进误当成内容正确。自动召回限制字段 `recallable=false` 也不同于 skip：一条早餐即使不参与自动召回，仍可能已经被写成 Event。

### 3.6 设计取舍及其依据

当前设计回应了早期原型中的三类问题。一个全局分组原型未能兼顾非连续承接与邻近经历分离，成对关系中的错误连接还可能经传递闭包扩大误合，因此系统保留有序原文和可恢复的 Track。按局部活动变化细分的原型将同一工程的排查、修改与验证拆开，因而持续归线与 Event 选择分开执行。多层复审探针则既有结果不变，也有分组更碎的情形，促使设计把职责和输入约束作为明确的检查对象。这些记录构成设计动机，其执行条件与历史原型范围见附录 A1–A7。

输入合同和表示能力同样限制可取得的结果。人工补齐前文，或在 metadata 中提供窗口外信息，会使下游成功与系统的自动找回能力脱节。若一条混合消息同时被要求不可拆、唯一归属，却又必须完整支持两段经历，表示本身就可能不存在合法解。当前合同因此分别规定阅读范围、归属单元与 bridge 共享；早期 Subevent/父级组织仍只作为历史原型保留。附录 A8–A9

规则选择还必须同时保留“应合”与“应分”的保护例。一次旧修订虽然缓解了目标案例的过拆，却把保护案例中的独立请求合并，因而被撤回；§3.2 的延迟案例则促使作者修订原评价。本文据此分别记录实现缺陷、规则取舍、未获支持的解释与作者判断修订，完整研究史见附录 A。

### 3.8 实验后的实现演进

在 2026-09-09 核对的部署版本中，普通 Track 的经历边界按具体事项的推进、完成、验证或实质修正判断；仅有相同人物、作品或理解背景不足以构成合并依据。前一段已经形成落点、后一段由新触发开始另一项活动时，系统通常将其分开。已有回复并不必然结束一段经历；话题仍可讨论，也不表示存在需要跨段延续的未完成事项。滚动工程策略作为例外保留，E10 提供该规则的两案局部观察（§5.9）。

该版本的 Writer 输入包含前一版正文，作为内容遗漏的对照；其绑定原文完整进入 owned，承担事实依据。绑定原图连同来源、顺序和角色一并提供，使文本与图片的送达路径可以核对。

截至 2026-09-13 核对的实现，Curator 冻结来源归属后直接交由 Writer 成稿，独立证据整理模型及其附加的证据要点、引语锚点、置信度和 Scene 候选判断已从生成路径撤除。自用部署将成功生成的结果送往 Bridge 记忆信箱，该路径不写入 Serein；是否允许普通自动召回仍由独立字段控制，进入信箱也不等于已生成 Scene。

宿主按原文绑定检索、去重并固定已有 Scene，向 Curator 与 Writer 提供相同对照，帮助识别已记录的经过；Scene 不授予新的来源归属。Curator 同时获得带来源标识的原图，相关转写随冻结归属传给 Writer。需要更新受保护前版的提案及其共享对话单元的依赖提案一起延后，无关提案继续处理。写作校验则保留结构检查和模型自审，撤除仅凭词形或词频判定文风与事实违规的规则。

公开发行版采用不同的落库路径：宿主校验与幂等结算成功后，Event 直接写入 Serein 记忆库，不经过 Bridge 信箱。自用部署的 Bridge 信箱路径和旧真实服务实验继续按各自实际使用的后端与停止位置报告。提交、配置与核对范围见附录 F。后续部署核对只确认实现状态，未新增完整日批或语义回归结果；E1–E10 的实验条件与计数保持原样。

### 3.9 Event 保存后的使用接口

Event 已用于新对话窗口的上下文注入，本文称为开窗注入，用于接续既有经历。对话进行中的按需召回由 Serein 负责索引与候选生成，聊天宿主负责实际交付。

召回卡片可以携带来源标识，使系统能够按 ID 读回原始对话、核对依据并补看上下文。叙事卷则把相关记忆组织为较长叙事；当召回记忆已被纳入叙事卷且关联可以确定时，系统可提供材料菜单，按需读取叙事正文或其中包含的材料。

来源关联为后续阅读提供入口。候选命中、最终选中、实际交付和按 ID 读取分别对应不同的操作记录；接口依据、使用者陈述及单独的召回测试见补充材料。

评价沿处理链分层进行：消息是否可见、归属单元如何处置、经历如何组织、正文是否忠实，以及保存是否完成，分别构成不同的检查对象。

| 维度 | 检查对象与判据 | 不能由它推出的结论 |
| --- | --- | --- |

## 5. 结果与失败分析

结果按故障机制与检查对象组织。§5.1–5.3 追踪来源保存、错误拒绝与角色丢失；§5.4 和 §5.9 给出入选及边界对照；§5.5–5.8 分别检查自检自报、因果归因、文本校验和补读返回。同一次执行既可能支持一项结构性结论，也可能同时暴露另一类错误。

### 5.1 来源保存与语义错误并存

E1 的真实服务回执记录首夜写入 6 条、次夜写入 6 条，其中 5 条各有一个前身。五次续接均保留旧来源，提交来源与最终 API 读回一致，旧记录保留为 superseded。同一执行中，例行早餐仍被建立并续接，若干已经获得回应的主动消息也在进入 Curator 前被排除。来源保存与语义错误在该次执行中同时出现。

主动消息漏传源于数据粒度不一致：过滤逻辑在单条归线成员记录（membership）内寻找使用者回复，而 Router 按消息保存这类记录。后续回复虽然存在，却不在同一成员记录中。最终 cursor 到达 65，阶段输入仍缺少相关原文。E2 的首夜输入和 Event 来源包含了此前缺失的主动消息；两次执行的代码差异见执行规格。

### 5.2 合法历史共享被误拒绝

E2 第二夜，绘画与工程分别续接各自前身。两个前身合法共享来源，宿主却将继承的共享消息判为侵占“未选中”的另一前身，触发 `Track Curator source already belongs to an unselected base`。模型决定仍是分别续接两条经历。失败发生在宿主校验层；第二夜未提交，数据库仍为首夜状态，cursor 保持 33。

该案例表明，来源约束需要区分新增越界与合法历史继承。仅因一条来源也出现在其他 Event 中便拒绝，会破坏原本允许的共享及续接关系。

### 5.3 输入重建丢失共享角色

在 E3 的合成花盆与歌曲案例中，同一条消息分别谈及盆下纸张仍干和歌曲末字被提前切断。数据库内该消息仍标记为 bridge；次日只续接花盆一侧时，输入组装却把继承来源默认填成 primary_activity，Writer 随后将歌曲内容写入花盆 Event。数据库中的旧标记没有改变，错误发生在读取后的输入重建阶段。

在 `070b2bc` 的 E5 重写及 E6 输入记录中，继承角色得以保留，E5 花盆重写也没有再次混入歌曲内容。输入记录定位了角色传递路径，正文对照及同时变化的条件见 §5.5。

### 5.4 入选与跨日承接的对照

E4 的十二道局部开发题与冻结作者预期一致。其中，包含菜名、数量及收拾清单的例行汇报仍被跳过；有具体感受和回应的交流入选；几个简短结果续接先前经历。这支持“具体名词或字数不是本批唯一判断依据”的有限观察。

E6 将类似对照放入连续交错材料。旅行中的借书、留言、看雨与归还延续同一经历；工程修复的不同阶段保持同一建设线；第一晚共同做蛋饼与第三天回想续接，第二天便利店蛋饼汇报被跳过，第三天苦汤及换汤交流形成新 Event。九组例行片段均跳过，作品和共读范围的纠正接回相应旧 Event。逐项阅读未发现明确的误入选、误合或碎拆。

“三日 6→6→7”中的前两个 6 是事务适配器的实际结算结果，最后的 7 是只读 Curator 决定对应的数量。使用者在第三夜调整实验范围，因此该夜止于 Curator，未运行 Writer、证据生成或结算写入。

E9 的新材料中，补测得到录音授权、重复扣款、桌游信息共享、桌面处理四条 create 决定，来源集合与冻结作者首选一致。同一公交卡的充值问题与刮桌面用途分开；两个跨线消息被共享，其后只回应单一话题的消息没有误共享。早餐和晚安两组跳过。该补测处置了 38 条原文，首轮失败的开头两条仍无最终入选动作，不能报告全批通过。正例“处理好了”还附有明确的试听许可信息，因此也不是仅改变前情的同句最小对照。

### 5.5 自检自报与正文错误

E3 的错误花盆稿在七项自检中全部返回 true，却仍包含无关歌曲。自检结果与正文之间的这一冲突，说明自检自报不能替代正文审阅。

E5 的五条新稿均通过原生 Writer 校验且未触发修稿（repair）；花盆稿不再串题，但充电稿仍有“第二天”的相对时间指向含糊。该次重写同时改变了角色继承、通读要求和模型采样，记录的是这些条件下的输出差异。

### 5.6 例行标记归因未获支持

开发中曾怀疑，Curator 对图书馆讨论的漏收来自输入的 routine_only=true。这是作者构造并故意误标的压力题；该字段在旧输入中表示是否仅为例行内容，标记并非本次真实 Router 的输出。固定规则和原文、仅改变标记的后续对照中，图书馆在 true 和 false 下各三次均 create；纯早餐在两种条件下各三次均 skip。更关键的是，图书馆 true 请求与前轮失败请求逐字相同，前轮两次 skip，后轮三次 create。

E7 未观察到该标记引起的动作差异，同一请求跨执行的结果却发生了变化，原失败的原因因而仍未确认。撤除字段属于职责简化的设计取舍；该组对照未提供删除字段提高准确率的证据。

### 5.7 词级判定误拒绝有效正文

E8 的绘画初稿将“午饭后”用作练习时间，同时在舍弃内容清单（discarded）中排除午饭问候。旧校验仅因“午饭”同时出现在两处便拒绝正文，触发 repair；修稿删除了有依据的时间细节，且该修稿实际落库。词级校验把时间锚点误判为应舍弃的生活片段，造成了信息损失。

修复后的冻结响应回放使同一初稿直接保存。该回放复用原模型回答，五份请求仅在完整 Track 卡片顺序上不同，所检查的是宿主处理和保存行为。来源集合的结构关系可以精确比较，正文中的词语则需要结合其作用判断。

### 5.8 有界前文为空时的处理缺口

E9 开头只有“处理好了。／嗯，那先放一边吧。”。整个组件缺少对象，Curator 按提示允许的格式请求 `missing_subject` 前文；宿主在消息 1 之前找不到该 Track 的材料，抛出 `isolated Codex job requested Track context but no bounded context exists`，首轮执行随即停止。系统尚未形成 create、skip 或 defer 决定，该次执行记为流程中断。

### 5.9 新边界规则下的自然对话重新分组

## 6. 讨论、限制与未来工作

### 6.1 对研究问题的回答

对于 RQ1，持续归线保留了可随新消息延续的 Track，供 Curator 联合判断交错材料。E6 的做饭与作品讨论展示了跨线共享和跨日承接；局部题、E9 补测与 E10 重新分组进一步展示了词面相似与实质承接的区别。相同食物名不必连接两次经历，同一物品可以服务不同目标，跨日回想也可以返回既有经历。Track 提供持续的组织范围，最终 Event 边界仍由 Curator 判断。

对于 RQ2，持续归线与延迟结算的分工，使系统能够先保存话题关系，再在结算时判断 Event 的入选、边界和续接对象。其取舍体现在信息可见性上：E3 中尚未稳定的纠正留在缓冲区，E9 中缺少对象的短句触发了补读。延迟结算为后续信息提供了进入判断的机会，但到达时点、完整性条件与补读范围共同决定了实际可见材料；空结果也需要明确返回。

对于 RQ3，来源追溯需要同时检查来源集合、来源角色和续接关系。E1 的五次单前身续接保留了旧来源及前身—后继关系，E2 和 E3 则分别暴露了合法共享误拒绝与继承角色丢失。进一步核对自检、正文和保存结果，可以区分来源可读回、材料被正确使用和正文忠实这几个层次。阶段记录使这些差异能够定位到输入过滤、约束检查、来源重建或写作环节。

### 6.2 适用范围与评价限制

自动摘要不能保证完全准确。错误既可能发生在经历入选、边界与续接对象上，也可能出现在正文的人物归属、因果、时间指向、图片理解或重点保留中；反复续接还可能累积遗漏与失真。来源可读回、结构校验通过或模型自检全真，都不等于正文忠实。使用者可以对照原文手动修订；单纯措辞不顺与事实、归属错误应分别处理，后者需要核对相关来源及续接关系。人工修订是使用中的纠错方式，不能计作自动生成的正确结果，也不能代替系统质量评价。

本研究的范围受使用偏好与材料选择约束。大部分材料由开发者编写，E10 的自然对话也是定向选案；作者参考尚缺全面独立标注与争议裁定，c09 的事后确认仅解决一个具体案例。所报告结果适用于这些材料与记录偏好，不代表跨使用者、跨语言的总体分布。关系质量、幸福感及“被记住”的主观感受未作系统测量。

因果归因受到执行条件的限制。材料被复用，规则、代码和执行入口在开发中变化；采样设置和底层模型版本的记录不完整，执行者的表现也不能直接代表生产上游模型。E1/E2 存在多项代码差异，E5 同时改变角色继承、自检提示与采样，E7 的同一请求跨执行出现不同动作，E10 缺少旧规则对照与重复采样。固定回答回放评价的是宿主处理，不能用来检验模型对请求顺序的敏感性。这些条件使现有记录不足以估计总体准确率、稳定性或相对基线优势；相关工作中的数据集也未在本系统上运行。

执行覆盖同样有限：真实服务证据尚未覆盖多前身合并、Scene/Arc 引用迁移或下游召回；E6 第三夜与 E9 止于 Curator，E8 只定位一类词级误拒绝。前版正文对照与原图读取的语义效果也未进入主表评价。设计史提供原型动机，部署记录提供实现状态，二者均不替代当前架构的受控效果试验。

Event 已用于开窗注入。使用者在持续使用中报告，对话连续性和回答表现已有改善；现有材料尚未量化改善幅度，也未分离 Event 构建与其他上下文机制、模型及提示变化的独立贡献。使用者也报告对当前自动摘要整体满意，并愿意手动调整少量措辞；这一判断反映个人使用中的可接受程度，不是错误率测量。这些使用者观察作为参与式开发背景保留，§3.9 的召回记录另存为使用接口材料，均不计入实验结果表。

### 6.3 未来工作

经历边界的稳定性仍需在更广泛的材料中检验。值得重点研究的情形包括：同一句短确认在不同前情中的作用，同主题新活动与既有事项之间的界线，以及模糊指代、长间隔回流与合法共享。按原始经历或对话流划分开发集与留出集，并在执行前固定规则、参考答案和可接受替代，可以降低材料复用与事后裁定的影响。增量评价还应区分旧 Event 来自真实前批结果还是手工输入，以观察错误是否沿处理历史累积。

反复续接中的正文保留与多模态理解构成另外两项开放问题。来源仍可读回时，旧阶段的理由、独特发现或未完事项仍可能从正文中消失。内容评价可依据原文区分必要信息、可压缩重复和旧稿错误，再沿续接关系检查遗漏、失真与无依据新增；多模态评价则可分别考察图片送达、来源角色传递和内容理解。

架构分工与提示设计的相对作用，可在相同输入和执行条件下通过基线或单因素对照检验。若研究进一步扩展到使用效果，检索与问答任务可连接已保存的 Event、实际读取的材料和回答质量。

## 7. 结论

本文围绕持续归线、延迟结算与来源追溯组织 Event 构建。持续归线将交错消息保留在可延续的 Track 中；延迟结算把 Event 的入选、边界和续接对象留到结算时判断；来源归属、来源角色与显式续接关系共同保存更新依据，使其能够沿阶段输入、正文和保存状态接受核对。

案例展示了跨日承接与单前身续接中的来源保留，也定位了原文漏传、合法共享误拒绝、来源角色丢失及空前文处理中断。其共同启示是，可追溯 Event 需要把话题组织、边界判断和来源传递连起来，并分别检查每个阶段的实际结果。这套实现及案例记录为持续对话中的 Event 构建提供了可复核的系统经验。
